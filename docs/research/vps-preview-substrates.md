# VPS-Preview-Substrate: ausgereifte Wege für isolierte Docker-Stacks

Research für [VPS-Preview-Substrate recherchieren](https://github.com/glombik26/app-builder/issues/3).
Keine Produktentscheidung. Alle Behauptungen gegen Primärquellen.

**Frage.** Welche ausgereiften Wege gibt es, auf **einem** VPS pro Feature einen isolierten Docker-Stack mit eigener erreichbarer URL zu fahren — und denselben Host später für TEST und PROD mitzubenutzen?

**Kandidaten.** Coolify, Dokploy, CapRover, Traefik+Compose, Caddy+Compose, Kamal.

**Glossar** (wie in `CONTEXT.md`): Preview = isolierter Docker-Stack mit eigener URL für genau ein Feature auf DEV. Environment = DEV | TEST | PROD. Operator = genau eine Person.

**Wichtige Unterscheidung.** Coolify- und Dokploy-„Preview Deployments“ sind **Pull-Request-Lebenszyklen** (öffnen → deployen, mergen/schließen → löschen). Das ist nicht dasselbe wie ein Feature-Preview der Plattform. Die Tabellen unten trennen „eingebautes PR-Preview“ von „ein Compose-Stack als benanntes Resource auf demselben Host“.

---

## Gemeinsame Primitive (unabhängig vom Produkt)

Diese drei Mechanismen sind der gemeinsame Nenner. Die Produkte unterscheiden sich darin, wer sie bedient.

### 1. Compose-Projektname isoliert Stacks

Ein Compose-**Project** gruppiert Container, Netzwerke und Volumes. Derselbe `compose.yaml` kann zweimal auf derselben Engine laufen, wenn der Project-Name verschieden ist.

- „A project's name … is used to group resources together and isolate them from other applications or other installation of the same Compose-specified application with distinct parameters.“ Compose setzt das Label `com.docker.compose.project`. ([How Compose works](https://docs.docker.com/compose/intro/compose-application-model/))
- Default-Netzwerk heißt `<project-name>_default`. Override: `--project-name` oder `COMPOSE_PROJECT_NAME`. ([Networking in Compose](https://docs.docker.com/compose/how-tos/networking/))
- Explizite Use-Cases für eigene Project-Namen: „Create multiple copies of a single environment, useful for running stable copies for each feature branch“; auf einem CI-Host Builds entkoppeln; auf einem Shared Host Namenskollisionen vermeiden. ([Specify a project name](https://docs.docker.com/compose/how-tos/project-name/))
- Namensregeln: nur Kleinbuchstaben, Ziffern, Bindestrich, Unterstrich; muss mit Kleinbuchstabe oder Ziffer beginnen. ([Specify a project name](https://docs.docker.com/compose/how-tos/project-name/))
- Container-Namen: `<project>-<service>-1`. ([COMPOSE_PROJECT_NAME](https://docs.docker.com/compose/how-tos/environment-variables/envvars/#compose_project_name))
- Services in getrennten Projects sprechen sich **nicht** an, außer über ein gemeinsames `external`-Netzwerk. Hybrid: nur der öffentliche Service am Shared-Netz, DB nur intern. ([Connecting multiple Compose projects](https://docs.docker.com/compose/how-tos/networking/#connecting-multiple-compose-projects), [Hybrid networking](https://docs.docker.com/compose/how-tos/networking/#hybrid-networking))
- `internal: true` auf einem Netzwerk: kein Default-Gateway, von außen unerreichbar. ([Internal networks](https://docs.docker.com/compose/how-tos/networking/#internal-networks))

**Teardown.** `docker compose down` stoppt und entfernt Container und die vom Project angelegten Netzwerke. External-Netzwerke und -Volumes bleiben. `-v` entfernt named volumes des Compose-Files. `--remove-orphans` räumt Container auf, die nicht mehr im File stehen. `--rmi` entfernt Images. ([docker compose down](https://docs.docker.com/reference/cli/docker/compose/down/))

### 2. Wildcard-DNS ist die Hostname-Konvention

Ein `A`-Record `*.example.com → VPS-IP` macht jeden Subdomain-Hostnamen ohne weitere DNS-Änderung erreichbar. Das dokumentieren Coolify, Dokploy und CapRover als Voraussetzung für generierte Subdomains. Traefik/Caddy/Kamal setzen denselben Record voraus, sobald Hostnamen nicht einzeln eingetragen werden.

Coolify-Beispiele für generierte Namen, sobald ein Wildcard-Domain am Server gesetzt ist:

- Resource: `https://<uuid>.example.com` (Beispiel `vgsco4o.example.com`). ([Server introduction — Wildcard Domain](https://coolify.io/docs/knowledge-base/server/introduction#wildcard-domain))
- Preview: `https://<PRId>.<random>.example.com` bzw. Template `{{pr_id}}.{{domain}}`. ([DNS Configuration — Autogenerated Domains](https://coolify.io/docs/knowledge-base/dns-configuration#autogenerated-domains), [Applications — URL Template](https://coolify.io/docs/applications#url-template))

Dokploy-Preview-Muster (Custom-Domain-Abschnitt; Default ohne eigene Domain ist `traefik.me`):

- `preview-${appName}-${uniqueId}.traefik.me` bzw. Wildcard `*.mydomain.com`. ([Preview Deployments — Custom Domains](https://docs.dokploy.com/docs/core/applications/preview-deployments#custom-domains))

CapRover:

- App bekommt `appname.root.domain.com`. Root-Domain kommt aus dem Wildcard `*.something.mydomain.com`. ([Getting Started — Step 2](https://caprover.com/docs/get-started.html), [App Configuration — HTTP Settings](https://caprover.com/docs/app-configuration.html))

### 3. Wildcard-TLS braucht DNS-01; viele Einzelnamen brauchen Rate-Limits

- Traefik: ACME-v2-Wildcards „can only be generated through a DNS-01 challenge“. Doppel-Wildcards (`*.*.local.com`) gehen nicht. Jeder Domain+SAN löst eine Zertifikatsanfrage aus. ([ACME — Wildcard Domains](https://doc.traefik.io/traefik/reference/install-configuration/tls/certificate-resolvers/acme/#wildcard-domains))
- Caddy: Qualifizierender Wildcard nur als linkes Label (`*.example.com`). Let’s Encrypt verlangt dafür den DNS-Challenge. Ab Caddy 2.10 wird das Wildcard-Zertifikat für einzelne Subdomains wiederverwendet. Caddy rät zu Wildcards, wenn viele Subdomains CA-Rate-Limits belasten würden. ([Automatic HTTPS — Wildcard certificates](https://caddyserver.com/docs/automatic-https#wildcard-certificates))
- Caddy On-Demand TLS: Zertifikat erst beim ersten Handshake, **ohne** die Namen vorher in der Config. Muss enabled **und** beschränkt sein (`ask`-Endpoint). Nützlich, wenn Namen zur Startzeit unbekannt sind. ([Automatic HTTPS — On-Demand TLS](https://caddyserver.com/docs/automatic-https#on-demand-tls), [Caddyfile `on_demand_tls`](https://caddyserver.com/docs/caddyfile/options#on-demand-tls))
- Caddy warnt: Experimente gegen Production-ACME können Rate-Limits auslösen, die HTTPS bis zu einer Woche blockieren. Internes Limit: 10 Versuche pro ACME-Account / 10 Sekunden. ([Automatic HTTPS — Testing](https://caddyserver.com/docs/automatic-https#testing), [Errors](https://caddyserver.com/docs/automatic-https#errors))

Fakt für viele Previews auf einem Host: entweder **ein** Wildcard-Zertifikat (DNS-01, einmalig) oder **ein Zertifikat pro Hostname** (HTTP-01/TLS-ALPN-01, skaliert mit der Zahl der Previews und trifft CA-Limits).

## Coolify

PaaS mit Traefik (Default) oder manuellem Proxy. Compose-File ist bei Compose-Deployments die Source of Truth.

### Per-Stack-URL

- Domain-Felder erwarten FQDN inkl. Schema (`https://coolify.io`). Mehrere Domains kommagetrennt. Port im Domain-String mappt auf den **Container-Port**; der Proxy bleibt auf 80/443. ([Domains](https://coolify.io/docs/knowledge-base/domains), [Docker Compose — Domains](https://coolify.io/docs/knowledge-base/docker/compose#domains))
- Server-weites Wildcard-Domain: neue Resource bekommt Zufalls-Subdomain; Previews `https://<PRId>.random.example.com`. Template auf der Application änderbar. Default-Template `{{pr_id}}.{{domain}}`. Tokens `{{random}}` und `{{pr_id}}`. Ohne eigenes Wildcard-Domain: `sslip.io` (`<uuid>.<ip>.sslip.io`). ([DNS Configuration](https://coolify.io/docs/knowledge-base/dns-configuration#autogenerated-domains), [Applications — Preview Deployments](https://coolify.io/docs/applications#preview-deployments), [Server — Wildcard Domain](https://coolify.io/docs/knowledge-base/server/introduction#wildcard-domain))
- Compose-Magic-Vars: `SERVICE_URL_<ID>` erzeugt `http://<name>-<uuid>.<wildcard>`. ([Coolify's Magic Environment Variables](https://coolify.io/docs/knowledge-base/docker/compose#coolifys-magic-environment-variables))

### Wildcard-TLS

- `https://` im Domain-Feld: Proxy (Traefik oder Caddy) bekommt die Route, Let’s Encrypt wird angefordert, Renewal automatisch. Scheitert ACME: Self-Signed, Browser-Warnung. ([Domains — HTTPS & SSL](https://coolify.io/docs/knowledge-base/domains#https--ssl-certificates))
- Catch-All/`HostRegexp`: Proxy stellt **keine** Zertifikate für Catch-All aus. Für Subdomains eines konkreten Domain: Wildcard-Zertifikat. ([Catch Multiple Domains](https://coolify.io/docs/knowledge-base/domains#catch-multiple-domains))
- Traefik-Wildcard: DNS-Challenge Pflicht (HTTP-Challenge kann keine Wildcards). Labels `tls.domains[0].main` + `sans=*.domain`. Danach reicht ein Subdomain-FQDN; kein ACME-Roundtrip pro Resource. ([Wildcard SSL Certificates](https://coolify.io/docs/knowledge-base/proxy/traefik/wildcard-certs))
- Default-Proxy ist Traefik. Server-Doku: „Soon we will support Nginx & Caddy with fully automated configuration“ / Optionen Traefik oder Custom/None. Domain-Doku spricht bereits von Traefik oder Caddy. ([Server — Proxy](https://coolify.io/docs/knowledge-base/server/introduction#proxy), [Domains](https://coolify.io/docs/knowledge-base/domains))

### Isolation

- Jedes Compose-Deployment bekommt ein eigenes Netzwerk. Der Proxy wird in dieses Netzwerk gehängt. Ohne Domain und ohne Host-Port-Mapping bleibt der Service nur intern (`http://<service>:<port>`). Host-`ports:` umgeht den Proxy. ([Docker Compose — Making services available](https://coolify.io/docs/knowledge-base/docker/compose#making-services-available-to-the-outside-world))
- Resource Limits: Default keine. Setzbar, Verweis auf Compose-Spec. ([Applications — Resource Limits](https://coolify.io/docs/applications#resource-limits))
- Preview-Secrets sind von Production-Env-Vars getrennt. ([GitHub Preview Deploy — Scoped Secrets](https://coolify.io/docs/applications/ci-cd/github/preview-deploy#scoped-secrets))

### DEV / TEST / PROD auf einem Host

- Ein Coolify steuert den Localhost-Server und beliebige Remote-Server per SSH. Jeder Server hat **eigenen** Proxy; Traffic geht nicht über den Coolify-Host. Localhost als einziger Server: „not recommended as high server usage could prevent to use Coolify“. ([Server introduction](https://coolify.io/docs/knowledge-base/server/introduction))
- Viele Applications/Compose-Resources auf demselben Server = viele Stacks. TEST und PROD sind weitere Resources mit festen Domains, nicht ein eingebautes Environment-Objekt wie bei Dokploy.
- Eingebautes Preview ist PR-gebunden, default aus, GitHub-App für Automation. Löschung wenn PR gemerged/geschlossen. Public-PR-Deploys extra riskant (beliebiger Code auf dem Server). ([GitHub Preview Deploy](https://coolify.io/docs/applications/ci-cd/github/preview-deploy), [Applications — Automated Preview Deployments](https://coolify.io/docs/applications#automated-preview-deployments))

### Operator-Oberfläche

Moving parts: Coolify-UI + eigene DB, SSH zum Docker-Host, Traefik-Proxy, optional GitHub App, optional Build-Server, DNS-Validierung gegen 1.1.1.1 (änderbar). Proxy-Änderungen können „your entire application inaccessible“ machen. ([Traefik Overview](https://coolify.io/docs/knowledge-base/proxy/traefik), [DNS Validation](https://coolify.io/docs/knowledge-base/domains#dns-validation), [Build server](https://coolify.io/docs/applications#how-deployments-work))

### Teardown / Ressourcen

- PR-Previews: automatisch gelöscht bei Merge/Close. ([GitHub Preview Deploy](https://coolify.io/docs/applications/ci-cd/github/preview-deploy))
- Automated Docker Cleanup: Schwellwert (z. B. 80 % Disk) oder Cron. Überspringt laufende Deploys. Entfernt gestoppte Coolify-Container, ungenutzte Images, Build-Cache, alte Helper-Images. Volumes/Networks nur wenn explizit aktiviert (Datenverlust-Hinweis). ([Automated Docker Cleanup](https://coolify.io/docs/knowledge-base/server/automated-cleanup))
- Builds auf dem Deploy-Host sind „resource-intensive“; Doku empfiehlt optionalen Build-Server. ([Applications — Resource Management](https://coolify.io/docs/applications#how-deployments-work))

## Dokploy

PaaS mit Traefik. Applications vs. Docker Compose sind zwei Resource-Typen mit unterschiedlichem Domain- und Preview-Verhalten.

### Per-Stack-URL

- Zwei Domain-Quellen: kostenlose `traefik.me` (HTTP only, außer eigenes Zertifikat) oder gekaufte Domain mit Let’s Encrypt. ([Domains](https://docs.dokploy.com/docs/core/domains))
- Applications: Traefik-**File**-Provider, Hot-Reload, kein Redeploy. Compose: Traefik-**Docker-Labels**, Redeploy nötig. ([How Domains Are Managed](https://docs.dokploy.com/docs/core/domains#how-domains-are-managed))
- Compose empfohlen: Domains-Tab in der UI; Dokploy injiziert Labels + Netzwerk zur Deploy-Zeit. Preview-Compose zeigt das Ergebnis. Ohne Domain und ohne Isolated Deployments bleibt die Datei unverändert. ([Docker Compose Domains — Method 1](https://docs.dokploy.com/docs/core/docker-compose/domains#method-1-using-dokploy-domains-recommended))
- Application-Previews: Default `traefik.me`, Port 3000, Limit default 3. Custom: `*.mydomain.com`. Variable `${{DOKPLOY_DEPLOY_URL}}`. ([Preview Deployments](https://docs.dokploy.com/docs/core/applications/preview-deployments))

### Wildcard-TLS

- Application-Router: `tls.certResolver: letsencrypt` auf `websecure`. ([Domains — Applications](https://docs.dokploy.com/docs/core/domains#applications))
- `traefik.me` bleibt ohne Extra-Zertifikat HTTP. HTTPS: Domain kaufen. Compose-Manual: „For HTTPS, you can use Let's Encrypt or other SSL/TLS certificates.“ ([Domains](https://docs.dokploy.com/docs/core/domains), [Compose Domains — Important Considerations](https://docs.dokploy.com/docs/core/docker-compose/domains#important-considerations))

### Isolation

- Isolated Deployments (Templates default an): eigenes Netzwerk aus `appName`, alle Services dran, Traefik wird verbunden. Motiv: zwei WordPress-Instanzen würden sich sonst auf `dokploy-network` den Service-Namen `wordpress` teilen — Docker erlaubt das nicht. ([Isolated Deployments](https://docs.dokploy.com/docs/core/docker-compose/utilities#isolated-deployments))
- Ohne Isolation: Service muss auf `dokploy-network`; übrige Services muss der Operator selbst drauflegen. ([Compose Domains — Important Notes](https://docs.dokploy.com/docs/core/docker-compose/domains#how-it-works))
- Custom-Install, die Traefik als Swarm-Service statt Standalone-Container fährt: nach Reboot können Network-Referenzen zu Traefik weg sein → manuelles Redeploy. Offizielle Installation mit Standalone-Traefik hat das Problem nicht. ([Isolated Deployments — Installation Type](https://docs.dokploy.com/docs/core/docker-compose/utilities#isolated-deployments))

### DEV / TEST / PROD auf einem Host

- Project gruppiert Applications, Databases, Compose-Services **pro Environment**. „Every project supports multiple environments (for example `production` and `staging`), each with its own set of services and shared variables.“ ([Interface Overview — Environments](https://docs.dokploy.com/docs/core/interface-overview#environments))
- Application-Previews: nur GitHub-Integration, default aus, nur PRs gegen den konfigurierten Target-Branch, Cleanup bei Close/Merge, optionale Label-Filter. „We recommend not using preview deployments for public repositories, since external people can execute builds and deployments in your server.“ Limit default 3. ([Preview Deployments](https://docs.dokploy.com/docs/core/applications/preview-deployments))
- Compose-Seiten listen keinen Preview-Tab (Shortcuts: General, Environment, Domains, Deployments, Backups, … — kein Preview). Die Preview-Doku steht unter **Applications**. ([Docker Compose — Keyboard Shortcuts](https://docs.dokploy.com/docs/core/docker-compose#keyboard-shortcuts), [Preview Deployments](https://docs.dokploy.com/docs/core/applications/preview-deployments))

### Operator-Oberfläche

Moving parts: Dokploy-Panel, Traefik (File + Docker), Projects/Environments, Git-Provider, optional Remote-Server per SSH, Volume-Backups, Monitoring. Compose-Command ist fest; Custom Command **ersetzt** den Default vollständig. Bind-Mounts unter `../files/`; absolute Host-Pfade „will be cleaned up during deployments“. ([Docker Compose](https://docs.dokploy.com/docs/core/docker-compose), [Interface Overview](https://docs.dokploy.com/docs/core/interface-overview))

### Teardown / Ressourcen

- Application-Previews: Cleanup bei PR Close/Merge; Cap über „limit the number of preview deployments per application (default is 3)“. ([Preview Deployments](https://docs.dokploy.com/docs/core/applications/preview-deployments))
- Compose: löschen über die UI (General). Kein in der Compose-Doku beschriebenes PR-Preview-Cleanup.
- Advanced-Tab erwähnt „resources“ (neben Commands, Cluster, Mounts); keine dokumentierte Default-Quota für Compose-Stacks. ([Interface Overview — Advanced](https://docs.dokploy.com/docs/core/interface-overview#advanced))

## CapRover

Thin Layer über Docker/Swarm + Nginx. Compose ist **kein** First-Class-Deploy-Pfad.

### Per-Stack-URL

- Wildcard-A-Record Pflicht für HTTPS. App-Default: `appname.root.domain.com`. Beliebig viele Extra-Domains. Ohne Domain kein HTTPS. ([Getting Started](https://caprover.com/docs/get-started.html), [App Configuration](https://caprover.com/docs/app-configuration.html))
- Best Practice: Wildcard `*.server.domain.com`, als Root-Domain aber `something.server.domain.com` setzen, Dashboard unter `captain.something.server.domain.com`. ([Best Practices — Hidden Root Domain](https://caprover.com/docs/best-practices.html#hidden-root-domain))

### Wildcard-TLS

- Pro Domain: Button „Enable HTTPS“ → Let’s Encrypt, danach optional Enforce HTTPS. ([App Configuration — Enabling HTTPS](https://caprover.com/docs/app-configuration.html#enabling-https))
- Wildcard-Zertifikat: nicht der Default. Certbot-Override mit DNS-Plugin, z. B. `-d ${domainName} -d "*.${domainName}"`. ([Certbot Overrides](https://caprover.com/docs/certbot-config.html))

### Isolation

- Interne Erreichbarkeit ohne Port-Mapping: `srv-captain--<app-name>`. Alle Ports sind innerhalb des Captain-Clusters erreichbar. ([App Configuration — Port Mapping](https://caprover.com/docs/app-configuration.html#port-mapping))
- Compose: „Although Docker Compose [is] a feature in Docker CLI, it is NOT available in Docker API. This means CapRover cannot handle docker compose files.“ Parser akzeptiert nur `image`, `environment`, `ports`, `volumes`, `depends_on`, `hostname` — Rest wird ignoriert. Service-Namen werden zu `srv-captain--…` umgeschrieben. Alternative: `docker compose up` plus Join auf `captain-overlay-network` plus eine CapRover-App „Nginx Reverse Proxy“. ([Docker Compose](https://caprover.com/docs/docker-compose.html))
- Instance Count: beliebig, begrenzt durch Hardware; zu viel RAM/Disk „your system may crash“. ([App Configuration — Instance Count](https://caprover.com/docs/app-configuration.html#instance-count))

### DEV / TEST / PROD auf einem Host

- Viele Apps auf einer Instanz, jede mit eigenem Subdomain. Kein Environment-Objekt, kein PR-Preview in den zitierten Docs. TEST/PROD = weitere Apps oder weitere Custom Domains.
- Build läuft auf demselben Host wie der Serve; 512 MB können beim Build nicht reichen. Empfohlene Workarounds: Swap, lokal bauen, separates CI. ([Getting Started — Minimum RAM](https://caprover.com/docs/get-started.html), [Best Practices — Out of Memory when Building](https://caprover.com/docs/best-practices.html#out-of-memory-when-building))

### Operator-Oberfläche

Moving parts: CapRover-Container (Ports **80/443/3000 fest**), `/captain` Volume, Docker-Socket, Nginx, Certbot, optional npm-CLI (`caprover serversetup` / `caprover deploy`). Firewall: 80,443,3000,996,7946,4789,2377/tcp und 7946,4789,2377/udp (Swarm). Docker ≥ 25, kein Snap. Default-Passwort `captain42` bis Setup. ([Getting Started](https://caprover.com/docs/get-started.html))

`caprover deploy` schickt den **aktuellen Git-Commit**; uncommitted/`gitignore`-Dateien fehlen. ([Getting Started — Step 5](https://caprover.com/docs/get-started.html))

### Teardown / Ressourcen

- App löschen in der UI. Kein dokumentierter Preview-Lifecycle.
- Let’s Encrypt kann Mails für **gelöschte** alte Domains schicken; betrifft das neue Zertifikat nicht. ([Troubleshooting](https://caprover.com/docs/troubleshooting.html))

## Traefik + Compose

Kein PaaS. Ein Traefik-Container, Docker-Provider, ein Compose-Project pro Stack.

### Per-Stack-URL

- Router-Regel `Host(\`whoami.docker.localhost\`)` auf Service-Labels. `providers.docker=true`, `exposedbydefault=false`, gemeinsames Netzwerk `proxy` (expliziter `name:`). ([Exposing Services — Basic](https://doc.traefik.io/traefik/expose/docker/basic/))
- Hostname-Konvention ist frei: `feat-<id>.dev.example.com`, `test.example.com`, `app.example.com`. Traefik leitet nur, was ein Router matcht.

### Wildcard-TLS

- File-Provider für statische Zertifikate (Beispiel: Self-Signed `*.docker.localhost`). ([Enable TLS](https://doc.traefik.io/traefik/expose/docker/basic/#enable-tls))
- Let’s Encrypt: Certificate Resolver + `httpChallenge` auf EntryPoint `web` (Port 80 von LE erreichbar) oder `tlsChallenge` (Port 443) oder `dnsChallenge`. Storage-Datei (default `acme.json`). Renewal: 90-Tage-Zertifikate, Start 30 Tage vor Ablauf. Ungenutzte Zertifikate können trotzdem erneuert werden. ([ACME](https://doc.traefik.io/traefik/reference/install-configuration/tls/certificate-resolvers/acme/))
- Domain-Ableitung: `Host()` / `HostSNI()` der Router, oder `tls.domains`. Wildcard nur DNS-01. ([Domain Definition](https://doc.traefik.io/traefik/reference/install-configuration/tls/certificate-resolvers/acme/#domain-definition))
- Docker-Labels für Resolver: `traefik.http.routers.<name>.tls.certresolver=le`. HTTP→HTTPS-Redirect am EntryPoint möglich. Öffentliches DNS nötig; lokale `*.localhost`-Namen bleiben Self-Signed. ([Generate Certificates with Let's Encrypt](https://doc.traefik.io/traefik/expose/docker/advanced/#generate-certificates-with-lets-encrypt))

### Isolation

- Compose legt `<project>_default` an; Service-DNS nur **innerhalb** des Projects. Zweiter Stack: anderer Project-Name, gleiches File. ([Networking in Compose](https://docs.docker.com/compose/how-tos/networking/))
- Traefik-Beispiel hängt App **und** Traefik an `proxy`. Für Isolation: App-Frontend zusätzlich an `proxy` (external), DB nur am Project-Netz. ([Use an existing external network](https://docs.docker.com/compose/how-tos/networking/#use-an-existing-external-network), [Hybrid networking](https://docs.docker.com/compose/how-tos/networking/#hybrid-networking))
- `exposedbydefault=false`: nur explizit gelabelte Container sind im Proxy. ([Basic guide command](https://doc.traefik.io/traefik/expose/docker/basic/))

### DEV / TEST / PROD auf einem Host

- DEV = N Compose-Projects (`-p feat-<id>`), TEST/PROD = zwei weitere Projects mit festen Hostnamen. Ein Traefik, Ports 80/443 einmal. Kein eingebautes Environment-Objekt — Konvention liegt beim Operator / bei der Plattform.

### Operator-Oberfläche

Moving parts: Docker Engine, ein Traefik, `docker.sock` (read-only in den Guides), persistentes `acme.json`, optional File-Provider-Verzeichnis, Wildcard-DNS, Compose-CLI. Keine UI, kein Git-Hook, kein PR-Cleanup. Die Plattform müsste `up`/`down`, Labels/Hostnamen und Limits selbst fahren.

### Teardown / Ressourcen

- `docker compose -p feat-x down` entfernt Container + Project-Netz. `-v` nimmt named volumes mit. `--rmi` Images. External `proxy` bleibt. ([docker compose down](https://docs.docker.com/reference/cli/docker/compose/down/))
- Compose-Spec `deploy.resources` / `mem_limit` / `cpus` (Coolify verweist darauf; gilt für jedes Compose-File). Kein eingebauter Disk-Schwellwert.

## Caddy + Compose

Kein PaaS. Ein Caddy als Reverse Proxy vor Compose-Projects.

### Per-Stack-URL

- Site-Adresse in der Caddyfile aktiviert Automatic HTTPS. `reverse_proxy` zu `host:port` (Container-Name, wenn Caddy im Docker-Netz ist, sonst publizierter Port). ([Automatic HTTPS — Activation](https://caddyserver.com/docs/automatic-https#activation), [reverse_proxy](https://caddyserver.com/docs/caddyfile/directives/reverse_proxy))
- Catch-all ohne Host: `https://` — vorgesehen für On-Demand TLS, wenn Namen nicht vorher feststehen. ([Caddyfile Concepts](https://caddyserver.com/docs/caddyfile/concepts), zitiert in der Automatic-HTTPS-Doku)

Caddy hat **keinen** Docker-Label-Provider in den zitierten Official Docs. Neue Previews brauchen entweder Caddyfile-Reload, JSON/Admin-API, oder On-Demand plus dynamisches Upstream (Platzhalter im Upstream **müssen** einen Port enthalten; Health-Checks behandeln sie als ein statisches Upstream). ([reverse_proxy — Upstream addresses](https://caddyserver.com/docs/caddyfile/directives/reverse_proxy#upstream-addresses))

### Wildcard-TLS

- Automatic HTTPS, sobald A/AAAA auf den Server zeigen, 80/443 erreichbar, Data-Directory schreibbar/persistent, Name in der Config. HTTP wird auf HTTPS umgeleitet. Public names: Let’s Encrypt oder ZeroSSL, mit Failover. ([Automatic HTTPS — Overview / Activation / Issuer fallback](https://caddyserver.com/docs/automatic-https))
- Wildcard-Site `*.example.com` → ein Wildcard-Zertifikat; Let’s Encrypt → DNS-Challenge (Provider-Modul). ([Wildcard certificates](https://caddyserver.com/docs/automatic-https#wildcard-certificates), [DNS challenge](https://caddyserver.com/docs/automatic-https#dns-challenge))
- On-Demand: Zertifikat beim ersten SNI, ohne Namen in der Config. Pflicht: `tls on_demand` **und** globale Restriction (`ask ?domain=` → 2xx). Ohne Restriction in Production unsicher. ([On-Demand TLS](https://caddyserver.com/docs/automatic-https#on-demand-tls), [`on_demand_tls`](https://caddyserver.com/docs/caddyfile/options#on-demand-tls), [`tls` `on_demand`](https://caddyserver.com/docs/caddyfile/directives/tls))

### Isolation

Identisch zu Traefik+Compose auf der Engine-Seite (Project-Name, interne Netze). Caddy muss das Frontend-Netz erreichen. Kein automatisches „nur gelabelte Container“.

### DEV / TEST / PROD auf einem Host

Wie Traefik+Compose: N Projects + Hostnamen. Unterschied: Routing-Config lebt in Caddy, nicht in den Stack-Labels. TEST/PROD = weitere Site-Blöcke oder dasselbe Wildcard + andere Upstreams.

### Operator-Oberfläche

Moving parts: Caddy, persistentes Data-Directory (`$HOME` muss schreibbar bleiben), Compose-CLI, optional DNS-Plugin (Wildcard), optional `ask`-Service (On-Demand), Admin-API default `localhost:2019` (`admin off` macht Reload ohne Restart unmöglich). ([Storage](https://caddyserver.com/docs/automatic-https#storage), [`admin`](https://caddyserver.com/docs/caddyfile/options#admin))

Weniger TLS-Mechanik als Traefik (keine Resolver-Namen, Default-HTTPS). Mehr Routing-Mechanik, sobald Stacks kommen und gehen (Reload oder On-Demand+Ask).

### Teardown / Ressourcen

- Compose: gleiches `down -v` wie oben.
- Caddy räumt Storage periodisch (`storage_clean_interval`, default 24h; Scan beim Start). Häufige Reloads brechen laufende ACME-Transaktionen ab; Doku rät zu Batch-Reloads. ([`storage_clean_interval`](https://caddyserver.com/docs/caddyfile/options#storage_clean_interval), [Errors](https://caddyserver.com/docs/automatic-https#errors))

## Kamal

Deploy-CLI (Ruby-Gem oder Docker-Image) + `kamal-proxy`. Kein Compose-Orchestrator.

### Per-Stack-URL

- `proxy.host` / `proxy.hosts`: Proxy routet nur diese Hosts. Ohne Host: alles, außer Hosts anderer Apps auf demselben Proxy. ([Proxy — Hosts](https://kamal-deploy.org/docs/configuration/proxy/#hosts))
- Mehrere Apps auf einem Server: **ein** Proxy, Boot-Config geteilt, „you'll need to manage it centrally“. ([kamal proxy](https://kamal-deploy.org/docs/commands/proxy/) — Navigationstext der Command-Seite)
- Accessories können hinter demselben Proxy liegen. ([Accessories — Proxy](https://kamal-deploy.org/docs/configuration/accessories/#proxy))

### Wildcard-TLS

- `ssl: true`: Let’s Encrypt über kamal-proxy. Voraussetzung: **ein** Server, `host` gesetzt, zeigt auf diesen Server, Port 443 offen. Default `ssl: false`. HTTP→HTTPS-Redirect default an. ([Proxy — SSL](https://kamal-deploy.org/docs/configuration/proxy/#ssl))
- Custom-Zertifikat aus Secrets (`certificate_pem` / `private_key_pem`), u. a. wenn mehr als ein Host. ([Custom SSL certificate](https://kamal-deploy.org/docs/configuration/proxy/#custom-ssl-certificate))
- Keine dokumentierte Wildcard- oder On-Demand-Option. Jede Preview-URL ist ein weiterer `host` plus LE- oder Custom-Zertifikat.

### Isolation

- Pflichtfeld `service`: Prefix der Container-Namen. ([The service name](https://kamal-deploy.org/docs/configuration/overview/#the-service-name))
- Modell: **ein** App-Image (+ Rollen) und separat gebootete Accessories (DB etc.). Accessories werden bei `deploy` **nicht** mitaktualisiert und haben kein Zero-Downtime. Default-Netz `kamal`. ([Accessories](https://kamal-deploy.org/docs/configuration/accessories/))
- Das ist kein Compose-Project. Ein Feature-Stack mit mehreren eigenen Services ist entweder mehrere Kamal-Apps (geteilt über `host`) plus Accessories oder außerhalb von Kamal.

### DEV / TEST / PROD auf einem Host

- Destinations: `kamal deploy -d staging` merget `config/deploy.staging.yml`. `require_destination: true` erzwingt `-d`. Secrets: `.kamal/secrets-common` plus `.kamal/secrets.<destination>` (nicht `.kamal/secrets`). ([Destinations](https://kamal-deploy.org/docs/configuration/overview/#destinations), [Require destinations](https://kamal-deploy.org/docs/configuration/overview/#require-destinations), [Environment variables](https://kamal-deploy.org/docs/configuration/environment-variables/))
- Destinations sind für langlebige Stände (staging/production) gebaut, nicht für N ephemere Feature-Stacks. Viele Previews = viele `service`-Namen oder viele Destination-Files.

### Operator-Oberfläche

`kamal setup` per SSH (default root): Docker via get.docker.com, Registry-Login lokal+remote, Image bauen/pushen/pullen, kamal-proxy auf 80/443, Container = Git-Hash, Proxy wechselt nach `GET /up` → 200, alte Container stoppen, unused Images/gestoppte Container prunen. Folge-Deploys: `kamal deploy`. Registry ist Pflicht. ([Installation](https://kamal-deploy.org/docs/installation/))

Moving parts: Ruby oder dockerisiertes Kamal, Registry-Account, SSH, `deploy.yml` (+ Destination-Files), `.kamal/secrets*`, kamal-proxy, Accessories separat.

### Teardown / Ressourcen

- Nach jedem Deploy: unused Images und gestoppte Container. `retain_containers` default 5. ([Installation](https://kamal-deploy.org/docs/installation/), [Retain containers](https://kamal-deploy.org/docs/configuration/overview/#retain-containers))
- `kamal prune`: löscht älter als die letzten 5 Container/Images. ([kamal prune](https://kamal-deploy.org/docs/commands/prune/))
- `kamal app remove`: nur App-Container/Images. `kamal remove`: App **und** kamal-proxy **und** Accessories **und** Registry-Logout — auf einem Shared-Proxy-Host trifft das auch andere Apps. ([kamal remove](https://kamal-deploy.org/docs/commands/remove/), [kamal app](https://kamal-deploy.org/docs/commands/app/))

## Passung DEV (viele Previews) / TEST (ein Kandidat) / PROD (ein Stand)

Alle sechs können **technisch** mehrere benannte Workloads auf **einem** Host mit verschiedenen Hostnamen fahren. Die Passung zur Plattform-Semantik (Preview = Feature-Stack auf DEV, nicht PR) ist ungleich.

| Semantik der Plattform | Was die Quellen hergeben |
| --- | --- |
| Viele ephemere Feature-Previews | Compose-Project-Name ist dafür explizit vorgesehen („stable copies for each feature branch“). Coolify/Dokploy können dasselbe als N Resources. Ihr **eingebautes** Preview ist PR-scoped und bei Dokploy für Compose nicht dokumentiert. CapRover: N Apps, Compose-Stack zerfällt in Einzel-Apps oder liegt neben CapRover. Kamal: N `service`-Deployments, jedes mit Image+Registry. |
| Ein TEST-Kandidat | Überall ein langlebiger Stack mit festem Host. Dokploy hat dafür Environments. Kamal hat Destinations. Coolify/CapRover/Compose: zweite Resource / zweites Project. |
| Ein PROD-Stand auf demselben VPS | Dieselbe Mechanik wie TEST. Coolify rät davon ab, den Coolify-Host selbst unter Last als einziges Target zu nutzen. CapRover-Builds konkurrieren mit PROD um RAM. Kamal `ssl: true` gilt nur bei genau einem Server. Isolation ist überall Konvention (eigene Netze, keine Host-Ports, keine geteilten Volumes). |
| Freigabe DEV→TEST→PROD | Kein Kandidat modelliert Freigabe. Kamal-Destination und Dokploy-Environment sind die nächsten eingebauten „zweiter Stand“-Hebel. |

## Schmalster Pfad für einen Operator (Moving Parts, keine Wahl)

Zählen, was der Operator **außerhalb** der Plattform am Leben halten muss, wenn das Ziel „N isolierte Compose-Stacks + URL, später TEST/PROD daneben“ ist.

1. **Compose + ein Reverse Proxy (Traefik oder Caddy)**  
   Minimum: Docker Engine, ein Proxy-Container auf 80/443, ein persistentes ACME-Store, ein Wildcard-A-Record, `docker compose -p … up/down`.  
   - Traefik: Routing entsteht aus Labels im Stack — neue Preview = kein Proxy-Reload, wenn das File die Labels schon trägt. Wildcard-TLS = DNS-01 **oder** ein Zertifikat pro Hostname.  
   - Caddy: weniger TLS-Konfiguration (Automatic HTTPS, optional On-Demand). Dafür Routing-Config außerhalb des Stacks, plus entweder Reload oder `ask`-Endpoint.  
   Die Plattform spricht Docker/Compose direkt. Kein zweites Control-Plane-Schema.

2. **Coolify oder Dokploy**  
   Dazu: deren Panel, deren Zustand, deren Traefik, deren Resource-Modell. Gewinn: UI, Domain-Buttons, optionales PR-Preview, Dokploy-Environments, Coolify-Disk-Cleanup. Kosten: die Plattform muss deren API/UI-Modell (Application vs Compose, PR-Preview ≠ Feature-Preview) mappen. Compose-natives Feature-Preview ist bei beiden „eine Resource anlegen“, nicht der eingebaute Preview-Schalter. Dokploy Isolated Deployments sind der dokumentierte Schutz vor Service-Namenskollisionen.

3. **CapRover**  
   Dazu: Swarm-Ports, Nginx, Certbot, fest verdrahtete 80/443/3000, CLI. Compose-Stacks sind kein natives Objekt. Schmal nur, wenn jedes Feature **eine** App ist, nicht ein Compose-Stack.

4. **Kamal**  
   Dazu: Registry, SSH-Deploy, Destination-Files, Accessories-Lifecycle, geteilter Proxy (Boot-Config zentral; `kamal remove` ist host-weit). Schmal für ein TEST + ein PROD. Für viele ephemere Multi-Service-Previews mehr Teile als Compose+Proxy, weil das Produkt kein Compose-Project ist.

Faktische Reihenfolge nach **Anzahl zusätzlicher langlebiger Teile** (nicht nach Komfort): Compose+Proxy < Coolify/Dokploy (zweite Control Plane) ≈ CapRover (Swarm+Nginx+Compose-Lücke) < Kamal für viele Previews (Registry+Destination-Matrix+kein Compose).

## Implications for the substrate decision

Fakten, keine festgezogene Wahl.

- Das Plattform-Preview ist ein **Feature-eigener Compose-Stack mit Hostname**, nicht das PR-Preview von Coolify/Dokploy. Deren Preview-Schalter (PR öffnen/schließen, Dokploy-Limit 3, nur Applications/GitHub) decken den Feature-Lebenszyklus nicht ab. Nutzen der PaaS für die Plattform wäre „Resource anlegen/löschen“, nicht „Preview Deployments einschalten“.
- Compose-Project-Namen plus ein Shared-Proxy-Netz nur für das Frontend sind der in der Docker-Doku beschriebene Weg, denselben Stack N-mal und TEST/PROD daneben auf **einer** Engine zu isolieren. Das können Traefik+Compose und Caddy+Compose direkt; Coolify erzeugt pro Compose-Deploy ein Netz; Dokploy tut dasselbe, wenn Isolated Deployments an sind.
- Ein `A`-Record `*.<dev-zone>` auf den VPS ist bei allen URL-pro-Feature-Varianten die dokumentierte Voraussetzung. Hostname-Konvention ist frei wählbar (`<feature>.dev.…`, `<pr>.…`, UUID). TEST/PROD können außerhalb der Wildcard liegen (`test.…`, Apex).
- TLS für viele kurzlebige Namen: entweder DNS-01-Wildcard (Traefik, Caddy, Coolify-Traefik, CapRover-Certbot-Override) **oder** ein Zertifikat pro Name (HTTP-01) und damit CA-Rate-Limits (Caddy dokumentiert wochenlange Sperren und interne 10/10s). Kamal-LE ist an „ein Server + gesetztes `host`“ gebunden, nicht an N dynamische Namen. Caddy On-Demand vermeidet hart kodierte Namen, verlangt aber einen `ask`-Endpoint.
- TEST und PROD auf demselben Host sind bei keinem Kandidaten ein zweiter VPS: zweite Resource / Environment / Destination / Compose-Project. Die Trennschärfe liegt in Netz, Volumes, Secrets, nicht im Produkt. Coolify warnt vor Last auf dem Coolify-Host selbst; CapRover-Builds teilen sich RAM mit dem Serve.
- Teardown, das zur Feature-Lebensdauer passt: Compose `down -v` ist vollständig und synchron. PaaS-PR-Cleanup ist an GitHub-PRs gekoppelt. Coolify-Disk-Cleanup räumt Images/Cache, Volumes nur opt-in. Kamal `remove` ist auf einem Shared-Proxy zu grob; `app remove` + `prune` ist die feinere Stufe.
- Der schmalste Pfad für **einen** Operator, der ohnehin eine Plattform schreibt, die Feature-Previews besitzt, sind die wenigsten langlebigen Teile: Docker Compose Project + ein Proxy. Coolify/Dokploy sind schmaler, wenn der Operator **keine** eigene Orchestrierung bauen und stattdessen deren Resource-Modell akzeptieren will. CapRover ist schmaler nur ohne echte Compose-Stacks. Kamal ist schmaler für ein oder zwei langlebige Destinations, nicht für viele Feature-Previews.
- Offene, hier nicht entschiedene Punkte (liegen in der Map unter „Not yet specified“): konkrete Domain/DNS-Zone, gleichzeitige Preview-Obergrenze, ob DNS-01 (Wildcard) oder HTTP-01/On-Demand, und ob die Plattform Docker direkt oder eine PaaS-API spricht.
